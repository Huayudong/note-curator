# 查重-合并规则

本文件规定「命中旧笔记后如何合并」。核心原则：**优先追加补充；原笔记确有错误时才改写**。
对应 `config.yaml.dedup`：`merge_flow: preview_then_write`，`default_op: append`。

## 1. 总原则：优先增，有错才改

合并 = 把新内容作为补充追加到旧笔记；只有原内容**确有错误**时才改写。

- ✅ **优先 append（追加）**：补充新要点、新增小节、在已有小节末尾加几条。这是默认且最常用的做法。
- ✅ **允许 edit（改写）的情况**——仅当原笔记确有问题：
  - 事实性错误（如「大模型无法部署」这类已被证伪的结论）
  - 明显笔误、错别字、断链
  - 严重过时（如某工具/参数已废弃）
- ❌ **不要为这些做 edit**：
  - 「换一个我更喜欢的说法」——尊重作者原有措辞，不改写风格（包括不因去 AI 味而改写旧笔记）。
  - 「重新组织结构」——只增不调序。
  - 删除大段原有内容（除非该内容明确错误，且预览里标注了删除理由）。
- **追加片段也是写作**：新增的片段按 `writing-style.md` 写成与旧笔记融为一体的中文，不是把源文剪一段贴进去。
- **frontmatter 一字不动**：合并不向 frontmatter 追加/修改任何字段（三字段铁律见 `obsidian-adapter.md` 第 2 节）；来源留痕由脚本写进正文文末。

> 为什么偏向追加：旧笔记的措辞、结构、双链锚点是有意为之的；过度改写会破坏个人风格。但遇到明确错误也不该放过——所以是「优先增、有错才改」，不是「一律不改」。

## 2. 判定流程（LLM 负责）

拿到 `find_duplicates.py` 的候选清单后：

1. 对 Top-N 候选，结合两篇正文做语义判断（脚本只给关键词初筛，语义裁决由 LLM 完成）。
2. 估算主题相似度（0~1）。≥ `similarity_threshold`（默认 0.65）→ **命中**，走合并；< 阈值 → 走新建。
3. 命中时，逐条决定每个要补的点用 `append` 还是 `edit`：
   - 旧笔记没有的新知识 → `append`。
   - 旧笔记有但写错了的 → `edit`（精确替换那句）。
   - 新旧都有且一致 → 不操作。

## 3. patch 文件格式（喂给 `write_note.py merge`）

patch 用操作块组织，一个 patch 可含多个 `## APPEND` 和 `## EDIT`：

```markdown
---
source: "https://example.com/a"          # 来源（必填，缺失填「本地草稿」）；有实际变更时由脚本追加为正文文末「来源补充」行
---

## APPEND ## 核心要点
（要追加的 markdown，原样接到「## 核心要点」小节末尾）
- **补充**：……

## APPEND EOF
（追加到文件末尾；EOF = 文件末尾，指定的小节不存在时会自动新建该小节）

## EDIT
<<<OLD
原笔记里需要被改写的精确字符串（必须逐字匹配，否则会跳过避免误改）
>>>NEW
替换成的内容（留空表示删除该段，但删除需谨慎并在预览确认）
```

说明：
- `## APPEND <section>`：`<section>` 是目标小节标题（如 `## LLM`、`### 参数`）。写 `EOF` 表示文件末尾。小节不存在时脚本会自动补标题再追加。
- `## EDIT`：OLD 必须是原文里**逐字一致**的字符串（含标点、空格）。匹配不到时脚本会 `SKIP` 而不是乱改——这是安全保护。
- 多个块按顺序应用。append 前会自动做**重复检测**：若片段（去空白后）已存在，该块标 `SKIP-DUP` 跳过，绝不重复写入。

## 4. 冲突处理（新旧结论矛盾）

新旧结论矛盾（如旧说 X 好、新说 X 差）时，按情况：
- **有定论的错误**（旧结论已被证伪）→ 用 `edit` 修正，并在预览里说明。
- **无定论/看场景**（如「X 在长文本更优」vs「X 总体最优」）→ 不覆盖，用 `append` 补充新结论并标注分歧，例如：
  ```
  - **补充（不同结论）**：另一来源指出 X 在长文本场景才更优，短文本未必——具体见评测。
  ```
- 拿不准时，默认只 append 不 edit，并在预览 diff 里突出，由用户人工裁决。

## 5. 来源留痕（强制，写在正文文末）

每次有实际变更的合并，`write_note.py --apply` 自动在旧笔记**正文末尾**追加：

```
---
来源补充：<来源URL或'本地草稿'> - YYYY-MM-DD
```

- **不写 frontmatter**。frontmatter 三字段（author/created/tags）保持一字不动；旧笔记里留有历史 `updated`/`sources` 字段的，原样保留，不主动清理。
- patch frontmatter 的 `source` 必填，缺失时填 `本地草稿`。
- 这样任何时候都能追溯某段补充/修改来自哪里，且属性区保持干净。
- 若某次 patch 全部被 SKIP（无实际变更），则不追加任何留痕。

## 6. 何时该「合并」而非「新建」

| 情况 | 动作 |
|------|------|
| 新内容与旧笔记**同一主题**，补充更多细节/新角度 | 合并到旧笔记 |
| 新内容是旧笔记里某概念的**子主题**且篇幅大 | 通常新建，并对旧笔记建双链；除非旧笔记该处很单薄，则合并 |
| 新内容与旧笔记只是**同一领域但不同主题** | 新建（如「CNN」与「RNN」是两个主题） |
| 旧笔记有错误，新内容是来**纠正**的 | 合并并用 edit 修正错误 |
| 不确定 | 默认新建（更安全），并对旧笔记建双链关联 |
